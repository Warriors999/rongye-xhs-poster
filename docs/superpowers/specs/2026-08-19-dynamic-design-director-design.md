# 动态设计导演：针织玩偶小红书微海报设计规格

**日期：** 2026-08-19  
**状态：** 待用户审阅  
**产品类型：** 手机端、小范围自用 Web 工具  
**目标输出：** 3 张具有设计感、文字排版和 AI 场景的 3:4 小红书微海报

## 1. 设计结论

网站不再采用三套固定模板，也不要求用户具备专业设计能力。用户只需上传一张针织玩偶照片，并输入一句简单想法或几个关键词；系统负责理解、发散、研究参考、形成设计方案、生成海报和质量检查。

固定的不是版式，而是质量原则：主体保真、文字克制、信息真实、层级清楚、适合手机浏览。每次生成的 3 张图拥有不同的设计假设，但不会变成简单的换背景或随机装饰。

上一版的手机端、无登录、小范围自用、下载成品等产品基础继续保留；上一版的固定 `cute / daily / series` 模板、复杂编辑器和独立图片美化流程不再作为主流程。

## 2. 目标用户与成功标准

### 目标用户

- 女性针织玩偶内容创作者；
- 有真实玩偶资产和普通拍摄照片；
- 需要制作小红书发布图片；
- 有主题想法，但不擅长构图、配色、排版和视觉表达；
- 主要使用手机，小范围自用，不需要社区、账号体系或公开作品库。

### 用户成功标准

用户上传照片并输入一句想法后，可以在一次流程内获得 3 张可比较的微海报，并能理解每张图为什么这样设计。用户不需要打开编辑器、不需要选择复杂参数，也不需要自己写专业生图提示词。

### 产品成功标准

- 主体仍然是用户上传的真实针织玩偶；
- 3 张结果在构图、气氛、排版或叙事上有明确差异；
- 结果像微海报，而不是“原图加一行字”；
- 不虚构价格、日期、商品名称、编号、规格或用户未提供的事实；
- 生成失败或单张质量不合格时，不影响其他合格结果交付；
- 手机上能看清、能选择、能下载。

## 3. 非目标范围

首版不做以下内容：

- 用户手动设计画布和复杂图层编辑；
- 蒙版、画笔、局部重绘和精细抠图；
- 多图拼贴和批量账号管理；
- 登录、会员、社区、作品公开展示和数据分析；
- 自动生成价格、日期、商品规格或销售文案；
- 依赖 Codex 本地 Skill 才能运行的线上服务。

## 4. 手机端用户流程

### 4.1 上传与想法

首页只保留一个主要任务：上传照片并输入想法。

输入内容：

- 一张玩偶照片，支持相册选择或拍照；
- 可选创作想法，例如“想做成春天的感觉”“温柔治愈”“像童话里的小店”；
- 可选补充文字，只有用户明确提供的文字才允许进入海报。

如果用户不填写想法，系统根据玩偶本身提出设计方向，不阻塞生成。

### 4.2 生成进度

使用简单的阶段提示：

`看懂玩偶 → 理解想法 → 研究视觉 → 形成方案 → 生成 3 张 → 质量检查`

进度页显示上传图片缩略图和当前阶段，不展示模型原始返回、不展示复杂技术日志，也不承诺不可控的精确百分比。

### 4.3 结果选择

结果页展示 3 张完整微海报，每张包含：

- 海报预览；
- 简短方向名，例如“春日手作场景”“安静的童话小店”“编辑感展示”；
- 一句设计说明，解释构图或气氛的重点；
- 单张下载按钮。

页面提供“全部保存”和“重新生成”两个操作。首版不把用户导入复杂编辑器。

### 4.4 失败与重试

若只有一张不合格，页面仍然显示其余结果，并提供“重新生成此张”。若整个任务失败，保留上传图片和用户想法，允许一键重试。

## 5. 动态设计导演流程

### 阶段一：识别主体

多模态模型读取上传图片，输出主体保护信息：

- 玩偶类别和可见形象特征；
- 外轮廓和比例；
- 姿态、朝向和视线；
- 主色和辅助色；
- 针织纹理和手作质感；
- 帽子、围巾、花朵等关键配件；
- 图片中不应被修改的细节。

这部分的用途是保护真实资产，不是让模型重新设计一个相似玩偶。

### 阶段二：理解创作意图

模型把用户的自然语言转换为：

- 主题；
- 情绪；
- 故事或使用场景；
- 适合的小红书内容语境；
- 可能的色彩和材质方向；
- 需要避免的表达。

用户输入被视为创作意图，不被视为可以覆盖系统安全和设计规则的指令。

### 阶段三：轻量视觉参考研究

默认每次执行轻量研究，优先寻找与主题相关的视觉案例，提取以下可迁移信息：

- 主体与留白的比例；
- 视觉动线和构图重心；
- 色彩关系；
- 背景材质和光线；
- 文字数量、位置和层级；
- 装饰元素的数量与秩序。

研究结果只保存为设计特征摘要和来源说明，不将参考图直接拼进最终海报，也不要求复制具体作品。

线上部署时不能依赖本地 Codex Skill。设计类 Skill 的方法应沉淀为服务端的设计规则和提示词；Pinterest 研究应通过可配置的搜索适配器或已整理的参考库完成。搜索不可用时，自动退回内置设计知识库，不阻塞生成。

### 阶段四：生成动态 Design Brief

每次任务生成一份 brief，至少包含：

```ts
type DynamicDesignBrief = {
  subjectProtection: {
    identity: string;
    silhouette: string;
    pose: string;
    colors: string[];
    material: string;
    mustKeep: string[];
  };
  creativeIntent: {
    theme: string;
    mood: string;
    audience: string;
    story: string;
  };
  researchInsights: {
    sources: Array<{ title: string; url?: string }>;
    composition: string;
    palette: string;
    material: string;
    typography: string;
    density: string;
  };
  variants: Array<{
    id: string;
    direction: string;
    concept: string;
    composition: string;
    scene: string;
    elements: string[];
    copy: { title: string; support?: string };
    negative: string[];
  }>;
};
```

### 阶段五：生成 3 个设计方向

这 3 个方向不是固定模板，而是每次根据主题重新解释的设计角色：

1. **生活方式方向**：将玩偶放入可信的手作、居家或自然氛围中，突出材质和陪伴感。
2. **故事叙事方向**：围绕用户主题构建一个小型场景，让玩偶成为故事主角。
3. **编辑海报方向**：强调设计师式留白、强弱层级、字体排版和视觉秩序。

三张图必须共享同一份主体保护信息，但允许在场景、镜头、光线、排版关系和装饰预算上产生差异。

## 6. 文字设计规则

图片模型直接生成完整海报文字，但提示词必须把文字控制在低复杂度范围：

- 默认只有一个短主标题；
- 可选一句很短的辅助句；
- 最多两个用户明确提供或模型从主题中安全提炼出的标签；
- 不生成价格、日期、编号、商品名、规格、产地或品牌信息；
- 用户没有提供具体名称时，不擅自给玩偶命名；
- 英文只在具有明确设计意义时出现，不随机添加；
- 文字必须位于安全区，不能遮挡玩偶主体；
- 若模型文字质量异常，降低文字量后重试。

质量检查发现乱码或虚构信息时，优先重新生成该张，不在网页端额外叠加未经检查的文字。

## 7. 模型与服务架构

### 模型职责

- 多模态模型：图片识别、用户意图理解、参考摘要合并、Design Brief 生成、质量检查；
- 图片模型 `gpt-image-2`：依据上传图片和设计 brief 生成完整微海报；
- 参考研究适配器：连接 Pinterest 或其他可用搜索来源，输出结构化参考摘要；
- 本地规则层：保留主体、文字、信息真实性、构图密度和失败回退规则。

多模态模型和图片模型可以通过同一个中转站使用不同模型名和路径。两者职责分开，便于替换模型和控制成本。

### 推荐调用顺序

1. 校验并压缩上传图片；
2. 多模态模型生成主体分析和创作意图；
3. 参考研究适配器返回有限数量的参考摘要；
4. 多模态模型合并 brief 并输出 3 个方向；
5. 图片模型并行生成 3 张海报；
6. 多模态模型批量检查 3 张结果；
7. 仅对不合格图片进行一次定向重试；
8. 返回合格图片、设计说明和可选来源说明。

### 可靠性边界

所有模型返回都必须经过本地 schema 校验。结构化返回异常时依次采用：清理代码围栏 → 提取首个有效 JSON → 使用字段默认值补全 → 走本地设计 fallback。客户端永远只收到安全的统一错误，不返回密钥、原始响应或内部提示词。

## 8. 成本与等待控制

首版不追求零成本，而追求成本可预测：

- 参考研究限制来源数量和摘要长度；
- 同一次任务只生成 3 个方向，不无限发散；
- 三张图片并行生成；
- 质量检查采用一次批量判断；
- 只重试不合格图片，最多一次；
- 研究失败时使用本地规则，不重复调用；
- 进度页显示“预计需要一点时间”，不显示未经确认的价格。

后续可以增加“快速模式”，跳过联网参考研究；首版默认使用标准轻量研究模式。

## 9. 页面与视觉设计

### 首页

暖白背景、单一主操作、上传预览、想法输入框和“生成 3 张微海报”按钮。页面不展示模板列表，不把专业参数放在首页。

### 生成页

使用阶段状态和上传图片缩略图，表现“设计师正在分析和制作”，避免空白等待。

### 结果页

以 3 张海报为视觉主体，卡片只保留方向名、设计说明和下载操作。主操作突出“保存全部”。

### 视觉语言

- 奶油白、低饱和暖色和少量粉彩；
- 圆角卡片和大触控按钮；
- 清晰的一级、二级文字层级；
- 不使用复杂仪表盘、技术日志和密集设置；
- 重点是生成结果，不是展示 AI 技术。

## 10. 数据与隐私

- 图片仅用于当前生成流程；
- 不建立公共作品库；
- 不要求登录；
- 生成结果由用户主动下载保存；
- 服务端不记录原始图片和完整提示词，除非后续明确增加历史功能；
- API 密钥只保存在服务端环境变量，不能发送到浏览器。

## 11. 验收标准

### 功能验收

- 手机端可以上传单张玩偶图并输入想法；
- 无想法时也能生成；
- 生成过程中显示阶段状态；
- 返回 3 张结果和 3 条简短设计说明；
- 可以单张下载和全部保存；
- 单张失败不会导致其他结果丢失；
- 参考研究失败时仍可正常生成。

### 视觉验收

- 3 张结果不是固定模板套用；
- 玩偶外形、姿态、颜色和针织质感基本保持；
- 背景、光线、材质和少量 AI 元素形成完整视觉场景；
- 有明显的微海报层级与排版；
- 文字少、清晰、无明显乱码；
- 没有虚构价格、日期、品牌、名称或商品信息；
- 没有模糊、严重变形、边缘毛刺、重复玩偶和杂乱特效。

### 工程验收

- schema 异常有容错和 fallback；
- API 错误不泄露内部信息；
- `pnpm test`、`pnpm typecheck`、`pnpm build` 通过；
- 在手机视口完成上传、生成、选择和下载关键路径；
- 生成文件真实存在、可打开且尺寸符合 3:4。

## 12. 实施边界

实施时优先改造现有 `/api/generate`、AI provider、提示词和结果页，复用已有上传、下载、测试和部署能力。暂不进行与动态设计导演无关的全量重构。

实施顺序应为：数据契约与 fallback → 多模态 brief → 参考研究适配层 → 图片提示词 → 结果页 → 质量检查与重试 → 测试和视觉验收。
